# Knowledge Work SDLC: design

This document maps the methodology onto exact source, installed, runtime, and
authority boundaries. [`docs/methodology.md`](docs/methodology.md) explains why
the operating model exists; the guides explain individual mechanisms.

## Definitions

- The **model** is the reasoning engine. The **harness** is the instructions,
  tools, declarations, artefacts, projections, and checks which shape its work.
  The host model plus harness in a running loop is the **agent**.
- The **main agent** is the agent the commissioner addresses. It acts as
  concierge during intake and orchestrator during a run. A **specialist
  definition** is harness for a bounded fresh worker; it is not another standing
  agent or manager.
- An **initiative** is the body of work one accepted intent sets in motion. A
  **run** is one composed attempt or follow-on pass within that initiative.
- A **recipe** is a human-readable tested route through method declarations. An
  **execution plan** is the run-specific composition the main agent records
  after adapting the recipe.
- An **expert extension** is an immutable project-owned method revision admitted
  by a professional lead and explicitly bound to one run. It is not a provider
  plugin or ambient memory.

## Completion object

```text
ordinary professional commission
→ visible, correctable interpretation
→ sufficient method composed by the main host agent
→ evidence-bearing candidate work product
→ real independent challenge when earned
→ user receives the result, material conditions and reachable evidence
→ consequential authority remains human
→ durable initiative/run/artefact state supports a fresh actor
→ governed feedback may improve one later bounded step
```

Validators, manifests, tests, file counts, and provider labels are evidence
about this transition. None defines it.

## Invariants

1. One main agent owns composition, dispatch, retry, replan, gates, and the run
   record.
2. Work moves across contexts through named durable artefacts.
3. Scripts enforce mechanical relations and never perform semantic routing.
4. Meaning inference, source evidence, model interpretation, host observation,
   and human authority remain distinct.
5. Project standing state is earned; templates and provisional files are not
   confirmed truth.
6. Protected originals are never experimental workspaces.
7. Capability is observed for the exact actor and operation, not inferred from
   a tool name.
8. Fresh recovery comes from the compact index, selected run, and named live
   outputs—not a generated recap.
9. Expert methods and lessons are eligible only through explicit human
   admission and run-specific selection.
10. Provider claims require their own native public-surface evidence.

## Nouns and ownership

```text
AGENTS.md + skills     operating logic
initiative index       identity, focus, status and run pointer
run record             composed plan, rationale, outcomes and gates
output artefacts        durable semantic substance
DESIGN.md               explanatory architecture
```

No `CASE.md`, universal current-state file, generated agent registry, semantic
stage catalogue, connector registry, or model router shares these authorities.

## Activation and continuity

```text
new commission
→ host discovers managed AGENTS contract or plugin entry skill
→ knowledge-work preserves exact wording and writes meaning + first run
→ same main agent composes from recipes/methods
→ kw-orchestration performs the plan

fresh session
→ compact initiative index only
→ user names/confirms initiative
→ kw-prime reads active/latest run + current meaning + required live outputs
→ kw-orchestration resumes the existing run or one linked successor
```

`knowledge-work` is the intake procedure, not an entry wrapper. `kw-prime`
reconstructs in the main context by reading the compact index directly; no
provider lifecycle hook is required. Repository installation projects the
empty index. In a fresh plugin workspace the entry skill initialises that same
neutral template when no initiative content exists; a missing index beside
retained initiatives triggers reconstruction rather than blank replacement.

The save order is semantic output, open run record, compact index. Closed run
records are immutable. A post-closure correction or authorised follow-on opens
one predecessor-linked successor.

Consequential delivery is owned by `kw-orchestration`, not a separate agent.
Its evidence-backed delivery procedure reconciles the explanation with the
current candidate and applicable records, then presents the substantive result
and its conditions before artifact availability or resolved-defect history.
`kw-prime` invokes the same duty for resumed returns. Supporting presentation
skills may assist composition without becoming a second source of authority.
The operating contract and these skill instructions supply the context path;
they do not mechanically enforce semantic compliance or prove comparative
quality.

## Composition and specialists

Six Markdown recipes live under `.knowledge-sdlc/recipes/`. Each contains one
machine-readable composition block plus prose describing applicability, gates,
degradation, and authority. The composition names order, human gates, and
run-specific narrowing. Method frontmatter remains the single authority for
method I/O, tools, capabilities, freshness, and independence.

`tooling/contracts.py` discovers actual methods and recipes and checks those
mechanical relations. It cannot select a recipe, evaluate a semantic trigger,
or execute a method. The main model adapts the nearest recipe and records every
inclusion/exclusion in the run record.

Skills run in the main context when interaction or reconstruction matters.
Specialists receive sealed durable paths, authority, exclusions, tools,
expected output, and stop condition. They cannot spawn or route. Review is
fresh and producer-independent when consequence earns it; otherwise the plan
may prune it visibly. A required but unavailable review degrades or blocks.

The plugin projection retains the canonical tool contract and emits Claude's
native `tools` allowlist, translating the internal `Shell` name to `Bash`. A
specialist receives no delegation tool unless its canonical contract names one.

## Project state and authority

Source templates declare `document_state: template`. Fresh installation creates
only the compact initiative index. A domain charter, source or model policy,
protected-artifact register, method directory, and learning index are rendered
from templates only when the work first earns that surface. Every new project
instance begins with `authority_state: provisional`, empty confirmation basis,
and a named writer. Consumers may use only confirmed normative fields. False,
provisional, stale, conflicting, or legacy prose may expose a question but
cannot override the present commission.

Ordinary safe work does not require a standing setup interview. Missing project
policy blocks only the consequential step that actually depends on it.

## Model boundary

The desired default for delegated work is the concierge model. If a host
exposes and accepts its exact identity, the orchestrator forwards it. Otherwise
the selector is omitted and the result is recorded as `unobservable`; provider
default is not reported as proven inheritance.

A different model requires an exact user override naming provider, model,
reasoning setting, scope, fallback, and effective revision. The harness never
chooses a cheaper, stronger, or different-family model autonomously. Model
identity does not grant authority or prove correctness/independence.

## Expert-owned methods

```text
explicit import request
→ kw-expert-extension preserves bytes and curates contract/authority/conflict
→ exact human/expert admission of immutable revision A
→ present run explicitly binds A
→ update creates B; old run still resolves A
→ suspend/retire removes new eligibility without rewriting history
```

Custody is under
`ai_docs/methods/extensions/<id>/revisions/<revision>/`. The methods index is an
opaque discovery view, not operative instruction. Optional provider-native
installation is a separate action and never selects a method. The core ships no
profession-specific expert method; a lead supplies and governs each extension.

Project context, expert methods, client templates, runtime capabilities, and
reusable lessons are distinct tailoring surfaces. Project context states
confirmed facts or rules. An expert method supplies a reusable procedure. A
client template constrains one native work product. A capability binding proves
what one actor can do now. A lesson is a governed possible influence from a
past correction. Presence on one surface grants no authority on another.

## Protected native work and capability

A template may be shape-, method-, or policy-bearing. Meaning and work order
bind exact identity, owner, precedence, editable/protected objects, native
features, candidate location, and conformance checks.

The orchestrator first checks facility visibility/reachability, then proves the
exact eventual actor can perform the required harmless operation. Bindings are
per run. The original remains unchanged; production targets a candidate.
Structural, formula, computational, visual, professional, and provenance checks
address different failures. Promotion requires exact human authority and a
recoverable observed operation.

## Provenance

```text
source entity
→ retrieval or transformation activity by identified actor/tool
→ durable snapshot/derivation
→ material claim, model range, or candidate output
```

A transport or MCP server is not the underlying evidence. Material work records
source/provider, identifiers, query/parameters, as-of and retrieval time,
entitlement/scope, retained result/hash, transformation, actor, uncertainty,
and downstream consumer.

## Governed personalisation

Resumption and personalisation do not share authority. Feedback first routes to
the current output, confirmed project context, reviewed failure pattern, or a
method-change initiative. Only a cross-initiative preference or bounded review
heuristic enters the deliberate lesson route.

The route is candidate → exact human disposition → opaque eligible cue → later
meaning frozen without lesson content → neutral nomination → bounded read-only
disclosure → one exact Select, Narrow, or Decline decision → one pending effect
→ treatment/control outcome → reversible disposition. The decision and run
record carry the bounded use; there is no separate activation object.
Provider-native memory is not an evidence source, continuity record,
personalisation mechanism, or fallback. If a host surfaces remembered content,
treat it as unverified ambient context until project evidence supports it.

## Source, workspace, and plugin shapes

```text
knowledge-work-sdlc/
  README.md  AGENTS.md  DESIGN.md  CHANGELOG.md  LICENSE.md
  install.sh
  .knowledge-sdlc/
    VERSION
    agents/
    skills/
    recipes/
    templates/
  docs/
    README.md  methodology.md  getting-started.md  guides/
  examples/
    manual-exercises/       optional prompt sheets and fixtures
  tooling/
  tests/
```

The source contains one authored skill corpus. A fresh workspace contains one
generated runtime corpus at `.agents/skills/`; it does **not** also contain
`.knowledge-sdlc/skills`. It receives managed agents, recipes, templates and
VERSION under `.knowledge-sdlc/`, one compact initiative index, and one
marker-owned `AGENTS.md` block. Other `ai_docs` state appears only when earned
and is immediately project-owned. These are ordinary repository files, not an
operating-system read-only mount; the install record makes edits to managed
files visible and requires explicit upgrade handling.

The plugin archive contains generated native skills/agents, provider manifests,
managed recipe/template resources, user documentation, and a licence. It
contains no profession-specific expert method. Generated views are deterministic
derivatives, not independently maintained authorities. Every generated skill
and agent states the relative path of the one shared resource root; the package
does not rely on a second copied prompt corpus.

## Tooling and installation

- `contracts.py`: method/recipe relation checks and source inventory.
- `projection.py`: pure workspace/plugin plans plus exact installed/plugin
  path-and-byte validation against canonical source.
- `installer.py`: explicit-target fresh install and install-record-owned guarded
  upgrade, with caught-error rollback and interrupted-upgrade recovery marker.
- `release.py`: deterministic archive and content manifest from a clean
  committed source.

An install record owns only generated harness files and the managed
AGENTS block. `ai_docs` becomes project-owned immediately and is never replaced
by upgrade. Unexpected process death may leave an explicit recovery marker;
normal upgrade refuses until recovery restores the recorded backup. No code
claims a universal filesystem transaction.

## Verification and claim boundary

Local tests attack relation, projection, containment, upgrade, and package
behaviour. They do not prove that a model produced useful professional work or
that a host supplied a fresh independent worker.

Native behaviour is inspected through representative real commissions:
natural activation, fresh-task continuation, protected native work, or
governed personalisation as relevant to the claim. A useful comparison may run
the same commission without the harness. Any result binds the exact host,
source revision, commission, and observed outputs. A fresh reviewer may
challenge a consequential result, but no repository-authored identity string,
path, status, or hash proves independence or promotes the product. An
unavailable provider surface remains unclaimed rather than blocking unrelated
supported use.

## Deliberate absences

There is no Python runtime in an installed workspace or plugin; no `sdlc`
command; no semantic case file; no automatic transcript append log; no
automated connector or model selection; no ambient expert method or lesson
activation; no cross-workspace personalisation claim; and no claim that a
static provider manifest proves execution on any host.
