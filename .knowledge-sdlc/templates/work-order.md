# Work order

Name revisions `work-order-r1.md`, `work-order-r2.md`, and so on. Preserve a
revision once a candidate or decision targets it.

## Identity
- Revision: `[rN]`
- Supersedes: `[prior path and hash or none]`

## Objective and judgeable output
Name the exact candidate object and intended use.

## Authoritative inputs
- settled meaning revision and any decision that established or changed it
- evidence map and required source snapshots
- protected target/snapshot where applicable
- live rival routes

## Requirements
### Must
Observable behaviours or changes.
### Should
Valuable but non-blocking work.
### Explicit non-scope
Objects, periods, scenarios, or conclusions that must remain untouched.

## Method and constraints
Professional treatment, transformations, model/tool allocation, and preserved assumptions.

## Expert-method binding

- exact extension/revision path and hash, plus admission decision
- allowed effect, explicit non-effect, precedence and conflicts for this run
- required inputs/outputs, actor, tools/capabilities and stop condition
- exact selecting authority

An eligible or provider-installed method is absent unless this work order and
the run record bind it.

## User-owned template binding
- path or provider reference, exact hash, ownership, revision and media type
- role: shape-bearing, method-bearing, policy-bearing, or combination
- precedence, allowed effect, and explicit non-effect
- editable ranges/objects and candidate output path
- protected ranges/objects and unchanged relations
- formulas, named ranges, calculation mode, links, macros, queries, and
  connections to preserve
- structural, formula, computational, visual, professional, and provenance checks

## Runtime capability binding
- semantic capability required by the method
- actual host tool or connector observed for this run
- actor that will execute the operation
- authentication, entitlement, asset reachability, and read/write scope
- reconnaissance performed and observed result
- harmless operation-specific probe or deterministic guarantee and result
- permitted operations
- fallback, degradation, and resulting claim limit

Absence of a binding is not permission to invent capability. This section is
per run; it is not a persistent connector registry.

## Candidate boundary
Descriptor requirements, native payload requirements, output root, protected-write prohibition.

## Validation
Positive checks, negative checks, template conformance, unchanged regions, and exact commands where mechanical.

## Stop and human checkpoints
Material ambiguity, missing source support, protected-scope conflict, or method contradiction.

## Claim ceiling and downstream consumer
State what the candidate may claim and which stage consumes it.
