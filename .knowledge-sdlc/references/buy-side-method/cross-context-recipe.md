# A bounded recipe inside the existing concierge–orchestrator

## Purpose

The concierge remains the only user-facing agent. Reuse the host's initiative/run, role dispatch, artifact, and disposition mechanisms. This is declarative routing guidance, not another orchestrator or a new active skill.

The underlying standard stays fixed while role contexts change. The method hypothesises that different inspection paths reveal failures; it does not guarantee decorrelation or reproduce a training-time gradient effect.

## 1. Clarify only what changes the work

Recover the user's immediate use, requested product, approved client modelling method, source policy, and edit boundary. Read supplied evidence before asking the user to restate it. If meaning is missing, invoke `derive-buy-side-decision-to-data` for the smallest unresolved unit.

One task may contain reported history and forecasts; declare their boundaries rather than force one interpretation on all sections. Freeze a brief adequate for this task revision. Record intended changes and acceptance-critical assertions before production.

Use an existing authorisation when it genuinely covers the action. Do not create a human confirmation ceremony for every routine step. Ask when scope, permission, a consequential modelling assumption, or a claim of use changes.

## 2. Establish the achievable route

Use existing preflight with [capability-and-runtime-binding.md](capability-and-runtime-binding.md). First inspect the materials; then check only capabilities the chosen task requires. Distinguish missing exact evidence from lack of broader search, and operational ability from permission.

Record the achievable product, calculation state, and assurance route separately. A workbook draft can exist without completed recalculation. A mapping plan can have thorough source review without any workbook write. A second human session may provide context separation without automated delegation.

Where the requested result cannot be achieved, explain the precise limitation and strongest permitted narrower result. Obtain a user choice only when the narrower route materially changes the commission. No unannounced source substitution or disclosure of client material to another service.

## 3. Produce a candidate

Invoke `produce-evidence-bound-model-candidate` with the task brief, applicable client skill/template, authorised evidence, critical assertions, and available operations. Provide only relevant context and tools. Do not paste the entire conversation or every installed reference.

Permit incomplete but useful work. Require reasonable bounded investigation and a concrete consequence for every important unresolved item. Freeze the candidate plus its compact coverage/change record and basis before another role judges it. “Frozen” means the version being judged is not silently edited; use existing copies/revisions, not a new state engine.

## 4. Choose assurance rather than multiplying roles automatically

For this method, a candidate claimed as independently checked always receives a fresh verifier for its critical assertions. If a genuinely separate context is unavailable, state the weaker status; the analyst may still choose to examine an unverified candidate manually.

Add blind re-derivation when an uncertain interpretation could reverse the task, source basis, or a consequential mapping. Dispatch the existing derivation skill with a bounded subquestion and original evidence, excluding the first answer. It need not reconstruct the entire model. Agreement is an acceptable result.

Add adversarial challenge for a materially new transformation, conflicting disclosure, protected judgment, suspicious reconciliation, or other plausible counterfeit-success path. Invoke `challenge-frozen-buy-side-candidate` in a different context. For routine established updates, the commissioned route may use critical verification without an additional broad reviewer; do not waive a review the user or existing policy requires.

If both blind re-derivation and challenge are used, compare the independent derivation only after it is frozen. Do not count agent agreement as proof, or repeatedly spawn dissenters until one produces a problem.

## 5. Verify and return feedback

Invoke `verify-discriminating-buy-side-claims` independently with baseline assertions, the unchanged candidate, original evidence, and precise challenge/disagreement propositions. An empty reviewer report does not waive the baseline. The verifier can add a bounded unflagged check within the agreed scope; it cannot become another endless donor audit.

The concierge distinguishes confirmed candidate defects, missing evidence/capabilities, defective acceptance, and method defects. These have different remedies. Do not rewrite the candidate to remedy an access failure or endlessly revise it under an unbounded acceptance condition.

A revision order contains the unchanged brief, exact candidate, supported defects, unresolved material questions, and protected parts. The producer changes only the authorised candidate. The reviewer and verifier never repair the object they assess. Retest changed dependencies, not unrelated branches.

## 6. Bound every loop

Default: one production candidate, one planned assurance cycle, and at most one targeted revision with affected rechecks. No automatic third revision. The limit ends autonomous iteration; it never causes a pass.

Capability repair has a separate bound: no repeated unchanged call after permission denial, unsupported operation, wrong account requiring user action, or declined approval. Allow one retry for an apparently transient failure. Any further retry needs new information or an explicit user choice. Preserve valid partial work and continue independent checks where useful.

Stop and return completed scoped work, completed work with residuals, partial work, blocked work, or a proposal to reframe. A known false claim cannot be accepted by renaming it residual. A withheld dependent conclusion need not block unrelated successful updates.

## 7. Context packets and handshake

| Role | Receives | Initially does not receive | Returns |
| --- | --- | --- | --- |
| Producer | Confirmed task, client method/template, allowed evidence, required outputs/checks, permissions | Unrelated history and irrelevant tools | Exact candidate, change/coverage record, basis and exceptions |
| Blind re-deriver | Original evidence, fixed task, bounded question, relevant analyst rules | First answer, selected mapping, expected defect | Independent interpretation and distinguishing evidence |
| Challenger | Frame, source access, candidate identity, protected surfaces; then candidate and mappings | Producer confidence; optionally mapping rationale until source-first watchpoints | Falsifiable decision-relevant challenges or none |
| Verifier | Baseline assertions, candidate, original evidence, neutral disputed propositions | Prior verdict as authority | Proposition results and checked scope |
| Concierge | Identified outputs and limits | No concealed requirement to remember uncommitted reasoning | One client-facing explanation and disposition request |

Reading original evidence before a producer rationale can reduce one exposure path, but does not establish statistical independence. If the host automatically copies history or shares other instructions, record that limit rather than claim a blind review.

## 8. The user should see the work, not the machinery

Return the candidate or proposed changes with a short account: what changed, what stayed, what matters, what was checked, and the one or few decisions the analyst must make. Keep routine provenance accessible behind the summary. Carry important conditions with the affected conclusion, not only in a distant appendix.

Do not install memory, scheduling, telemetry, a marketplace binding, or another workflow engine for this recipe. Evidence from an episode may justify a later skill revision; it does not automatically change the client's method.
